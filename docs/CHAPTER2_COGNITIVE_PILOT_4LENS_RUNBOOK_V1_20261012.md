# ムダギリ診断 第2章｜4視点・実ユーザーCognitive Pilot V1

日付：2026-10-12／PR #46 Draft／**未実施**。この資料は調査準備であり、実際の利用者をテストした結果ではない。

## 何を確かめるか

現状はコードとスマホQAで「内訳が表示される」ことは保証できる。しかし、①未確定の意味を理解し、②どの明細を確認すべきか納得し、③将来累計の条件を誤解せず、④ライフプラン相談が売り込みではなく任意の選択肢と感じられるかは**まだ証拠がない**。5〜8人の新規利用者に説明なしで見てもらう。

**UI設計で先に確保したこと**：`月最大の見直し候補 → 根拠付きの全カテゴリ内訳 → 1/5/10年の参考累計 → 第1章JOBと家計の答え合わせ → 確定改善機会・保障確認 → 任意のライフプラン相談 → 12カテゴリ敵図鑑`。確定改善額は厳格判定のため主役にせず、未確定候補も確約しない。

## 4視点と実測ゲート

| 視点 | 調査で見たい行動 | 自由回答の問い | 暫定合格のめやす（8人の場合） |
|---|---|---|---|
| 行動経済学 | 最初に見せた月最大額と内訳へ迷わず到達。タップせず根拠を探せる | 「金額は何の内訳？ まず何を確かめる？」 | 7/8人が追加説明なしで項目を挙げ、7/8人が自分の最初の確認行動を選べる |
| 心理学 | 圧迫感なく、未確定・条件付きの意味が分かる | 「この金額は必ず浮くと思う？ なぜそう思う？」 | 8/8人が保証額と誤解しない。不安・自己否定を誘う表現があれば優先改修 |
| マーケティング | 内訳→年数別→行動→面談の意味がつながる。面談を強要されたと感じない | 「必要なら何を誰に相談したい？ なぜ？」 | 7/8人が具体的な行動を述べられる。面談への関心は別途理由を質的に記録し、強要された回答をCV成功としない |
| バズ理論 | 内容が本人の言葉で説明できる／共有範囲が分かる | 「友達に見せるなら何をシェアしたい？ 金額が公開されると思う？」 | 8/8人が家計金額・保障・本人IDの非共有を正しく理解し、共有したい理由を自発的に話せるか定性的に確認 |

※8人未満で実施した場合は人数に応じて判断し、絶対的な統計的有意性を主張しない。上記は改修判断の暫定的な**質的UXゲート**であり、売上・継続CVの数値予測ではない。

## 実施順（1名あたり約10〜15分）

1. 同意：匿名の調査記録のみ。実際の口座・保険契約・収入・家計明細の提出不要。画面は架空データ版。録音・録画は別途明示的同意がある場合のみ。
2. 何も説明せず、[第2章テスト画面](https://mudagiri.github.io/mudagii/pilot/chapter12-answercheck-v1/chapter12-answercheck.html) の最初の月額まで読む。案内せずに「この金額は何を意味する？」と聞く。
3. その先を自分で進んでもらう。「内訳の名前と、なぜ候補になったか、次の確認先を説明して」と聞く。実際に必要だったスクロール・タップ数・誤操作を記録。
4. 1年5年10年の参考累計を見てもらい、「確実にこの額が貯まると思うか」「どんな条件付きか」を聞く。
5. 第1章JOB・答え合わせを見て、「新しく気づいたことは？ 性格が正しいと証明できたと思う？」と聞く。先に正解を教えない。
6. 保険の棚卸しについて「保険の加入や解約を勧められたと感じたか？」を聞く。保険内容把握済み／直近見直し済みケースはカード非表示であることを研究者側だけで確認。
7. ライフプラン相談を見てもらい、今の生活のどんな決定を確認したくなったかを聞く。相談に行きたいと言わせる誘導はしない。
8. 最後に共有カードを見てもらい、共有される情報を自分の言葉で説明できるか聞く。

## 観察票（各参加者1行、識別しないIDだけ）

`participant_code,device_width,chapter2_entered,understands_uncertain,finds_all_candidates,explains_basis_without_tap,identifies_first_action,understands_1_5_10_conditions,personality_no_false_validation,insurance_no_product_push,understands_share_privacy,consult_relevance_notes,friction_notes,verbatim_quotes_anonymized`

- 全項目は匿名回答。参加者名・家計金額・実際の保険契約・端末IDなどは保存しない。
- `understands_uncertain` が偽ならそのままメッセージを強化。1年5年10年の金額を「確定して浮く」と誤解したケースは公開の判断前に改善する。
- 適当にタップした／説明を読み飛ばした場合は「分かっていた」と評価せず、設計で改善する。

## 結果からの判断

- 必須理解（未確定の意味、条件付き将来累計、全候補の根拠、シェア範囲）の失敗が繰り返されるなら**UI修正して再Pilot**。誤解が残るなら正式リリースしない。
- 納得感が高くても「面談したい理由」が生まれない場合は、無理に第3章を足さず、生活設計に必要な問い・本人の次の一歩・相談で得られるものの説明を再設計する。
- 後続のA/Bでは第2章完了率、結果スクロール到達率、確認行動選択、共有率、**本人の意思による有効ライフプラン面談の予約成立数**まで計測。相談ボタンのタップだけを最終CVとしない。
- 4視点を毎回の設計→実装→QA→ユーザー検証のチェック列として管理。単に各分野の点数を記載して完了とは扱わない。
