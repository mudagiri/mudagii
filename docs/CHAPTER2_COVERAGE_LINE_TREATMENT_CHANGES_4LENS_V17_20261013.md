# 第2章 V1.7｜保障の見直し理由・公式LINE相談の専用導線／4視点監査

更新：2026-10-13。Draft PR #46の隔離プレビューのみ。本番変更なし。

## ユーザーからの指摘
「保障の相談で公式LINE飛ばすがない」「見直す理由って高い安いとか足りてないもそうだけど治療法が変わってて意味ないもあるよね」

現行のV1.6「保障の棚卸し」は理由の説明と任意の相談導線の前段を作っていたが、**保障カード自体に公式LINEの相談ボタンがなかった**。その結果、ライフプラン相談CTAへ流れてしまい、最も興味が高まった瞬間から保障の相談への経路が分かりにくい。

## V1.7変更

- 「保障の棚卸し」に**「公式LINEで保障の相談をする →」**を追加。詳細アコーディオンを開かずタップできる。
- **医療の変化**：入院中心から通院や薬物療法など治療方法が変わった場合に、契約している給付条件と対応しているか。
- **暮らしの変化**：家族、働き方、収入、公的保障が変わっても必要な保障になっているか。
- **保険料・重複**：金額だけでなく、払う保険料と給付条件のバランス、似た保障との重複はないか。
- **旧契約＝無意味**・**新契約＝正解**・**保障不足と確定**・**保険料が削減可能と確定**、はすべて禁止。古い契約に有利な給付条件・特約・継続メリットがあり得るため、変更や解約を勧める判定はしない。
- 保険料0円／入力対象外の場合、保険加入・民間保険契約が存在するとは仮定しない。「今ある公的保障や勤務先の制度がどこまで対応するか」の案内に言い換える。
- 「内容を把握している」「直近1年以内に確認した」人は従来どおり**カードとCTAとも非表示**。STYLE4種共通。
- 過去に開発した1年/5年/10年の金額演出、確定改善額、未確定の改善可能性の算式には一切触れない。保険見直しを金額として加算しない。

## 公式LINEへの実装契約

`ResultScreenChapter2V32.tsx` の保障カードに独立した `consultCoverage` を追加。相談者が明示的にボタンを押したときだけ：
- `chapter2_v32_coverage_consultation_clicked` イベントに匿名の `placement='coverage_review'`／`topic='insurance'`（金額、健康・医療履歴を送らない）。
- `onBeforeExternal()` で従来どおり結果の復帰・保存を保護。
- `onLine(coverageConsultHandoff(diagnosisId,handoffCode))` が存在すれば既存のアプリ側の公式LINE導線へ引き継ぐ。
- 引継ぎ：`placement='coverage_review'`、`consultPrimary='lifeplan'`、`consultSelectedTopic='insurance'`、`insuranceReview=true`。**相談の入口はライフプランの中の保障点検**であり、面談予約成立の確定ではない。
- `onLine` 未接続の場合は既存の**公式LINE** `https://lin.ee/ZeLu7i6`へ遷移。新しい公式URLを勝手に作らない。
- **`pilotNoExternalActions`の場合はURLを開かず、ユーザーに「調査用でLINE送信・予約はされない」と画面内で回答**。SNS、保険の個人情報をデモに送らない。

## 行動経済学・心理学・マーケティング・バズ理論の4視点

| 視点 | 必須条件 | 自動QAと実ユーザーでの反証 |
|---|---|---|
| 行動経済学 | 「気づき→理由→具体的な選択」を近接。余分な詳細タップを強要しない | 3理由と公式LINE相談CTAがアコーディオンを開かず見える、44px以上のタップ領域。ユーザーが何を確認するか自発的に説明できなければFAIL |
| 心理学 | 不安で煽るのでなく、旧契約の価値と新しい治療の変化を両立。保障の不足・医療給付の可否を断定しない | 文言監査で「古い保険は無意味・必ず削れる・絶対に不足」等の断定禁止。ユーザーが買い替えの強制と誤読すればFAIL |
| マーケティング | 「保障の棚卸し」に対応した専用CTAから、意図した相談テーマを正しく引き継ぐ。ライフプラン全般のCTAとは別 | テストはplacement/topic/insuranceReviewの契約を検証。実CVは有効な相談日程成立で確認。クリックやLINE友達追加だけではCVにしない |
| バズ理論 | 「医療や暮らしの変化によって保障の中身も確認」という話題性を持たせるが、本人の支出・健康・保険情報は共有しない | 共有画像は既存の匿名JOB/クリアのまま。LINE導線は本人の明示操作のみ。家計情報をSNSへ送らない |

## V1.8｜LINEの相談内容を実際に伝えるための補強（2026-10-13）

V1.7のコードだけでは、公式LINEの「友だち追加」URLへ遷移しても、`consultSelectedTopic='insurance'` がLINEのトーク本文へ自動送信されることを保証できない。標準 `https://lin.ee/ZeLu7i6` のままではWeb側の引継ぎオブジェクトがLINE運営画面に転記される仕組みも確認できない。

**利用者の導線：** 保障カード → 専用確認モーダル → 「相談文をコピーして公式LINEへ」 → LINEのトークで本人が貼り付けて送信。本文は `保障内容の確認について相談したいです。` と `引継ぎコード：MG-...` だけ。コピーできない環境では選択可能なテキストと「手動でコピーして公式LINEを開く」を出す。家計の金額・保険料・病歴は本文に含めない。送信そのものは利用者の明示操作で、トーク未送信でも予約済みと見なさない。

**既存システム：** `MudagiriAppV2` のGAS/ローカルリード保存は引き続き `ctaPlacement=coverage_review`・`consultSelectedTopic=insurance`・`insuranceReview=true` とコードを保存対象にする。外部 `onLine` コールバックだけは `externalLineContext` で保障相談の8キーに再生成し、入力額・家計データを流さない。通常のライフプラン相談の引継ぎ挙動は変更しない。

**自動QA範囲：** Chromium/WebKitで合計8画面幅に加え、隔離QAモード `?qaCoverageHandoff=1` で実際の保障モーダル・コピー・LINEコールバック・機微情報なし・外部送信なしを確認する。390pxではクリップボード拒否時の手動コピー経路も確認する。純関数では外部 `onLine` への余計なフィールドを遮断するテストを追加。

**未検証／本番統合の停止条件：**
1. GASの送信は `no-cors` のため、ブラウザからレスポンスの成功を直接判定できない。GAS/Sheet側でテスト用 `handoffCode` が保存されたか別途照合する。
2. LINE公式アカウント側で、利用者が貼り付けたコードと「保障相談」が担当者に届き、保存済みリードと照合できるか、人の手で確認する。LINE側の自動認識・自動返信連携は実装済みとは言わない。
3. 実際の診断から専用モーダルを経てLINEへ移動・診断結果へ復帰できるか実機確認する。プレビューは架空データ・GAS無効、運用データでの成功ではない。
4. 5〜8人のCognitive Pilotで、相談理由が自然に理解され、コピーの一手で離脱しないか検証する。面談日程の成立だけを最終CVとする。

### 4視点での差分

| 視点 | V1.8での対応 | 検証に残る点 |
| --- | --- | --- |
| 行動経済学 | カードでは理由とCTAを常時表示。追加モーダルはLINE本文が勝手に送られない誤認を防ぐための必要ステップ。 | 追加1ステップでの離脱 |
| 心理学 | コピー本文は任意の相談意思のみ。病歴・保険商品に触れず、買い替え強制もない。 | 不安・押し売りの印象 |
| マーケティング | 保障相談意図とコードをLINEトークにも運べる形にする。クリック、コード照合、面談成立を分ける。 | 実送信率・有効面談率 |
| バズ理論 | 公開SNSの共有カードは変更しない。保障相談は非公開チャット内だけで扱う。 | 自発的シェアを妨げないか |

FROZEN診断エンジン・12カテゴリ基準・`confirmedA`・`cUpper`・GAS API判定は変更しない。本番公開・ユーザー検証は未完了。


## V1.9.1｜相談ファネル計測と実運用データ確認（2026-10-13）

本番の分析Sheet（ムダギリ診断_ANALYTICS_V1）の`LEADS`タブをヘッダーだけ確認したところ、`receivedAt, leadId, diagnosisId, anonymousUserId, createdAt, source, toneMode, typeCode, typeName, annualIncomeBand, monthlyImprovement, firstQuest, leadJson`の13列で、`consultSelectedTopic`の専用列はなかった。したがってWeb側から`insurance`を送信したというだけで、運営が一覧画面でその意図を確実に識別できるとは結論できない。現時点でSheetの生データや列定義は変更していない。

Web側のイベントを以下に細分化した：
- `chapter2_v32_coverage_consultation_clicked`：保障相談の案内を開いた（送信未成立）
- `chapter2_v32_coverage_line_copy_success`：相談文がコピーできた（LINE送信未成立）
- `chapter2_v32_coverage_line_copy_failed`：コピー拒否などで手動転記が必要（LINE送信未成立）
- `chapter2_v32_coverage_line_message_outbound`：保障としてLINE遷移を開始（面談予約未成立）

これらのイベントの記録内容は`placement`・`consultSelectedTopic`のみで、保険契約情報・保険料・家計・相談文そのものは含まない。研究プレビュー`?qaCoverageHandoff=1`ではLINE/GASを実際に開かず、発火ステップだけを記録してChrome/WebKitで検証する。

本番前の手動停止条件は、①`leadJson`に`consultSelectedTopic=insurance`・`insuranceReview=true`・`handoffCode`が入ることをテスト用一件で照合する、②LINEチャットへ利用者がコードを貼り付けて送信した後に担当者がSheetとの照合を確認する、③相談者の意思表示と友だち追加だけの状態を混同しない、の3点。これは現時点では未検証。
